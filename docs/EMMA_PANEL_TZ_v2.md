## 1. Общее описание

Панель управления Эммой — раздел внутри Interfin AI-CRM, доступный только роли
`admin` и дополнительно защищённый PIN-кодом. Позволяет управлять поведением
Эммы без правки кода и деплоя:

- системный промпт с неограниченной историей версий и откатом;
- база знаний (загрузка файлов → автоматическая RAG-индексация);
- библиотека файлов, которые Эмма отправляет клиентам;
- справочник контактов и ссылок;
- приветствие `/start` и кнопка вызова менеджера;
- статистика работы, журнал ошибок, алерты.

### 1.1 Не-цели (осознанно за рамками v1)

- Создание/удаление ботов, несколько ботов — только Эмма.
- Редактирование Telegram-токена, ключа Anthropic, модели из панели.
- Роли с ограниченным доступом к панели.
- Полный конструктор команд и клавиатур (произвольные `/команды`,
  inline-кнопки, раскладка по сетке).
- Смена LLM-провайдера (в стеке зафиксирован Claude, `claude-sonnet-5`).

### 1.2 Принцип интеграции

Панель — это **UI поверх существующих механизмов CRM**, а не параллельная
система. Диалоги остаются в `leads`/`messages`, handoff — в M13,
база знаний — в pgvector (M4), уведомления в UI — через WebSocket (M9).
Новые таблицы создаются только там, где сущности ещё нет.

## 2. Доступ и безопасность

### 2.1 Роль

- Пункт меню «🤖 Эмма» виден только роли `admin` (в JWT `role=admin`).
- Все эндпоинты `/api/emma/*` — за `auth.Middleware` +
  `RequireRole(RoleAdmin)` + middleware PIN-сессии (см. 2.2).
  Роль `manager` получает `403` без деталей.
- Никакой роли «владелец» не вводится: владелец = существующий `admin`
  (CHECK в таблице `managers` не меняется).

### 2.2 PIN-код (6 цифр)

- **Первичная установка (bootstrap):** PIN в системе изначально не задан.
  При первом открытии панели admin видит экран «Установите PIN» (ввод дважды).
  До установки PIN ни один эндпоинт панели, кроме `pin/setup`, не работает.
- Хранение: bcrypt-хэш (cost 12) в таблице `settings`
  (ключ `emma_panel.pin_hash`; сервис settings расширяется строковыми ключами).
- **PIN-сессия:** после верного PIN создаётся запись в Redis
  `emma:pin:<manager_id>` с TTL 30 минут; каждый запрос к `/api/emma/*`
  продлевает TTL. JWT не трогаем (payload `{sub,role,iat,exp}` фиксирован M7);
  «привязка к session_token» из v1.0 не реализуема — session_token в CRM нет.
- **Брутфорс:** счётчик неверных попыток в Redis `emma:pin:fail:<manager_id>`;
  после 5 неверных — блокировка ввода на 15 минут (429 с `retry_after`).
- **Redis недоступен → fail-closed:** PIN-проверка и PIN-сессия при
  недоступном Redis отвечают 503, панель закрыта (в отличие от
  rate-limit M8, который fail-open: там деградация — пустить, здесь —
  не пустить).
- Смена PIN — по старому PIN. Сброс забытого PIN — только с сервера
  (one-off команда `cmd/reset-emma-pin`, по образцу `cmd/create-manager`).

### 2.3 Прочее

- Файлы (база знаний, файлы для отправки) хранятся вне web-root:
  `data/emma/{kb,files}/` (volume в Docker), имена — UUID, оригинальное имя в БД.
- Загрузка: allowlist MIME + сигнатура файла (не только расширение),
  максимум 50 МБ (это же лимит Telegram Bot API на отправку документов).
  В prod перед приложением стоит nginx — в его конфиг добавляется
  `client_max_body_size 50m` (иначе загрузка упрётся в дефолтный 1 МБ
  ещё до приложения).
- Каталог `data/emma/` — именованный volume в Docker-стеке и **включается
  в B2-бэкапы прода** (сейчас бэкапится только БД/WAL — файлы панели без
  этого не переживут потерю сервера).
- Все мутирующие действия панели логируются: `manager_id`, действие,
  сущность, timestamp (slog, как остальной аудит).
- Токен Telegram / ключ Anthropic: вкладка «Статус» показывает
  «задан/не задан» и результат последней проверки — значения не выводятся
  и через API не передаются никогда.

## 3. Вкладки панели

Экран панели (после PIN) — 6 вкладок. У всех вкладок общий UI-паттерн:
изменения копятся локально, жёлтый баннер «Есть несохранённые изменения»,
кнопка **«Применить»**. Перезапуск процесса не нужен: воркер читает
конфигурацию из БД с кэшем 30 секунд (тот же паттерн, что `internal/settings`),
т.е. изменения доезжают до Эммы максимум за 30 секунд.

### Вкладка 1 — Промпт

Сейчас промпт — константа в `internal/worker/prompt.go`. Переносим в БД.

**Поля:**
- **Системный промпт** — textarea от 20 строк, со счётчиком токенов.
- **Запретные темы** — теги (Enter — добавить, × — удалить).
- **Стиль общения** — выпадающий: Формальный / Дружелюбный / Нейтральный /
  Экспертный (дефолт — Нейтральный).

Поле «язык ответов по умолчанию» из v1.0 **исключено**: язык — свойство лида
(M14, автоопределение ru/en/es), языковая инструкция остаётся кодом.

**Сборка system-блока (порядок, код в `prompt.go`):**
1. системный промпт из БД (актуальная версия);
2. секция запретных тем: «Никогда не обсуждай: …» (из тегов);
3. секция стиля (короткая вставка по выбранному значению);
4. языковая инструкция M14 (код, не редактируется);
5. вставка про счета менеджера M12 (код, не редактируется);
6. активные контакты (вкладка 5);
7. список активных файлов для отправки с описаниями (вкладка 4);
8. RAG-чанки (M4).

**Бюджет токенов.** System-блок делят промпт, контакты, файлы и RAG-чанки.
Арифметика при прежнем лимите 2000 не сходилась (QA 2026-07-11: промпт 1200
+ 30 контактов ~600 + файлы ~300 + 5 RAG-чанков ~1500 ≈ 3600 — база знаний
вытеснялась), поэтому решением владельца `budget.system_prompt`
поднимается **2000 → 5000** (config.yaml; потолок входных токенов растёт
до 11000, отклонение от SRS §7.2 фиксируется в CLAUDE.md по образцу замены
модели). Правила:
- редактор показывает живую оценку токенов **той же метрикой, что
  `Budgeter`** (`len(bytes)/4`; кириллица ≈ 2 байта/символ, т.е. ~2 символа
  на токен — UI-счётчик обязан совпадать с воркером, иначе редактор будет
  врать);
- сохранение промпта длиннее **1200 токенов** блокируется с пояснением;
- лимит редактора — ключ `emma_panel.prompt_token_limit` в settings
  (дефолт 1200), меняется только с сервера.

**Проверка запретных тем** — только через промпт (секция «Никогда не
обсуждай»), пост-фильтрация ответа по подстрокам из v1.0 исключена
(ложные срабатывания типа «политика конфиденциальности»). Если на практике
промпта окажется мало — отдельным эпиком добавим LLM-классификатор ответа.

**История версий:**
- при каждом «Применить» старая версия остаётся в `emma_prompt_versions`,
  новая становится активной (одна активная — частичный уникальный индекс);
- версия включает промпт + запретные темы + стиль (**восстановление
  возвращает все три поля** — это явно написано в UI подтверждения);
- боковая панель: дата/время, автор, первые 100 символов; действия
  [Просмотреть] [Восстановить]; при восстановлении текущая версия
  автоматически уходит в историю;
- глубина истории не ограничена.

**Миграция:** первая версия в таблице создаётся миграцией из текущего
текста константы `prompt.go`; константа остаётся в коде только как
fallback на случай пустой таблицы (и помечается deprecated).

### Вкладка 2 — База знаний (RAG)

Управляет тем же индексом pgvector, который сейчас наполняется CLI
`cmd/index-kb` из `docs/kb`.

- Таблица файлов: имя, тип, размер, дата, **статус индексации**
  (`pending` / `indexed (N чанков)` / `error: …`).
- Загрузка: drag&drop / выбор файла. Форматы: **TXT, MD, PDF**.
- Конвейер: сохранить оригинал → извлечь текст (TXT/MD — как есть;
  PDF — извлечение текста, Go-библиотека выбирается в эпике; PDF без
  текстового слоя → статус `error`, OCR не делаем) → asynq-задача
  `emma:kb:index` → `rag.Indexer.IndexDocument(source, text)`.
  Индексация асинхронная: Voyage имеет rate-limit, большой файл может
  индексироваться минуты — статус виден в таблице, готовность приходит
  WS-событием.
- `source` чанков = `panel:<file_id>` — не пересекается с файлами
  `docs/kb` (те остаются на `cmd/index-kb`);
- **повторная загрузка файла с тем же именем обновляет ту же строку**
  `emma_kb_files` (upsert по `filename`, `id` не меняется) — тогда
  `source` совпадает и `ReplaceSource` атомарно заменяет старые чанки
  (QA-фикс: при новой строке на каждую загрузку старые чанки остались бы
  в индексе навсегда).
- [Переиндексировать] — на случай ошибки/смены модели эмбеддингов.
- [Удалить] с подтверждением: чанки source вычищаются
  (`ReplaceSource(nil)`), оригинал удаляется с диска.
- Объём базы не ограничен — в контекст Эммы попадают только релевантные
  чанки (порог `rag.similarity_threshold`, калибровка — `scripts/rag_calibrate`).

### Вкладка 3 — Файлы для отправки

Библиотека вложений, которые Эмма может отправить клиенту в Telegram.

**Поля файла:** название (внутреннее), **описание для Эммы** (когда
отправлять — например: «отправь, когда клиент спрашивает подробный прайс»),
файл (**PDF / JPG / PNG**; DOCX исключён решением владельца — редактируемые
документы клиентам не отдаём, Word-файлы сохранять в PDF перед загрузкой),
переключатель «Активен».

**Механизм отправки (маркер-протокол):**
- в system-блок добавляется секция: «Тебе доступны файлы для отправки
  клиенту: [id=3] Прайс 2026 — отправь, когда… Чтобы отправить файл,
  добавь в конец ответа маркер {{file:3}}»;
- воркер парсит маркеры `{{file:<id>}}` из ответа Claude, вырезает их из
  текста, валидирует id по списку активных файлов (несуществующий/неактивный
  id — маркер молча вырезается, ошибка в журнал) и отправляет файл(ы)
  после текстового сообщения: PDF — `sendDocument`, JPG/PNG —
  `sendPhoto`; несколько файлов — по одному сообщению на файл
  (`sendMediaGroup` не используется: не смешивает документы с фото,
  и подпись у альбома одна);
- отправленный файл фиксируется в `messages` служебной записью
  (`author='bot'`, текст `[файл: Прайс 2026]`) — менеджер видит в чате
  M12, что Эмма отправила клиенту;
- событие `file_sent` пишется в журнал событий (вкладка 6);
- **ретрай-ветка**: воркер сохраняет исходящее в БД до отправки
  (crash-safety M3) — сохраняется **очищенный** текст без маркеров
  (история диалога не должна учить Эмму подражать маркерам).
  Осознанное упрощение v1: если Send текста упал и сработала ветка
  переотправки, вложения к этому ответу не восстанавливаются
  (id файлов из маркеров живут только в памяти обработчика);
  ошибка пишется в журнал.

Тот же маркер-протокол используется для handoff (раздел 4) — один
парсер на оба случая.

### Вкладка 4 — Контакты и ссылки

Справочник, попадающий в system-блок (только активные записи).

**Поля:** тип (Телефон / WhatsApp / Telegram / Email / Сайт / Другое),
название, значение, комментарий для Эммы («давай, когда клиент готов
к консультации»), «Активен», порядок сортировки.

**Ограничение:** не более **30 активных** записей (бюджет system-блока);
UI показывает счётчик и суммарную оценку токенов секции.

Примечание: правило текущего промпта «не давай контактов, которых нет
в базе» начинает работать по-настоящему — контакты теперь структурированные.

### Вкладка 5 — Приветствие и вызов менеджера

Минимальные «сценарии» v1 (вместо полного конструктора из v1.0):

- **Приветствие `/start`** — редактируемый текст, отправляется без вызова
  Claude. Ветвление — **в воркере ранним выходом, НЕ в диспетчере**
  (QA-фикс: Kanban-хуки OnInbound — анти-спам, сброс TTL, last_activity —
  живут в воркере; ветка до очереди обошла бы их, и TTL лида тикал бы,
  как будто он молчит). Вебхук работает как сейчас: сохранить inbound →
  задача в очередь → 200; воркер после OnInbound и проверки режима видит
  `/start` с непустым welcome → шлёт welcome вместо вызова Claude.
  Ответ-приветствие сохраняется в `messages` как outbound (история полная).
  Пустое поле = поведение как сейчас (отвечает Эмма-LLM).
  Язык лида `/start` не выставляет — гард `!strings.HasPrefix(text, "/")`
  уже есть в коде M14 (проверено QA).
- **Кнопка «Связаться с менеджером»** — переключатель вкл/выкл + текст
  кнопки. При включении Эмма отправляет постоянную reply-клавиатуру с одной
  этой кнопкой **сразу с приветствия** (решение владельца) и далее
  прикрепляет её к ответам. Нажатие обрабатывается тем же ранним выходом
  воркера (точное совпадение текста). Смена текста кнопки в панели не
  обновляет клавиатуры, уже открытые у клиентов: нажатие старой кнопки
  придёт как обычный текст и уйдёт в Эмму — она распознает просьбу и
  поставит `{{handoff}}` (деградация мягкая, не потеря).
- **Текст подтверждения handoff** — что Эмма отвечает клиенту при передаче
  менеджеру (дефолт: «Сейчас свяжу вас с менеджером, ожидайте»).

Хранение — ключи `emma_panel.*` в `settings` (строковое расширение сервиса).

### Вкладка 6 — Статистика

Источники: существующие `leads`/`messages` + новый журнал `emma_events`.

**Метрики (период: день / неделя / месяц / всё время):**
- новые диалоги (лиды) и активные диалоги (входящие за последние 24 ч);
- сообщений: входящих / ответов Эммы;
- среднее и p95 время ответа Эммы (мс) — из `emma_events`;
- отправлено файлов (по каждому файлу — счётчик);
- handoff: сколько раз клиенты запросили менеджера;
- **расходы на Claude**: input/output-токены за период и примерная
  стоимость в $ (токены берутся из `usage` каждого ответа API и пишутся
  в `emma_events`; цены за 1M токенов — константы в коде с версией модели,
  сумма помечена в UI как «примерно, точный счёт — в консоли Anthropic»).

**Журнал ошибок:** таблица — дата/время, тип (`llm_api`, `telegram_api`,
`timeout`, `file_not_found`, `kb_index`), текст, lead_id; фильтр по типу
и периоду; пагинация (50 на страницу).

**Алерты в Telegram:**
- настройка `emma_panel.alert_chat_id` (id группы/чата владельца) — задаётся
  в этой вкладке; пусто = алерты выключены;
- условия: ≥3 ошибок LLM подряд (счётчик в Redis, сбрасывается успешным
  ответом); ошибка отправки в Telegram API 3 раза подряд; падение
  индексации базы знаний;
- формат: тип проблемы, время, текст последней ошибки;
- анти-шум: не чаще одного алерта одного типа в 15 минут;
- отправка — существующим ботом (Эммой) через `bot.Send` в указанный chat_id.
- Инфраструктурные алерты (процесс упал, Redis/Postgres недоступны) —
  остаются в Prometheus/Alertmanager (M11), панель их не дублирует.

### Порядок обработки входящего сообщения (сводно)

```
Вебхук: сохранить inbound → задача в очередь → 200   (правило §4.4, не меняется)
Воркер:
  1. Kanban.OnInbound — анти-спам, сброс TTL            (M5, не меняется)
  2. Проверка режима M13: human / пауза → выход         (M13, не меняется)
  3. РАННИЙ ВЫХОД ПАНЕЛИ (новое):
     /start и welcome непуст  → welcome + клавиатура, СТОП
     текст = кнопка менеджера → handoff (текст подтверждения), СТОП
  4. Сборка system-блока: промпт БД + темы + стиль + язык (M14)
     + счета (M12) + контакты + файлы + RAG (M4) → Claude
  5. Парсер маркеров ответа: {{file:N}} → файлы, {{handoff}} → режим human;
     маркеры вырезаются, в messages сохраняется чистый текст
  6. Отправка → messages → emma_events (reply, токены, время ответа)
```

## 4. Handoff — запрос менеджера клиентом

Строится целиком на M13 (`dialog_mode`, пауза Эммы, чат M12). Новое —
только **инициатива клиента**:

1. **Триггеры:** нажатие кнопки «Связаться с менеджером» (точное совпадение
   текста кнопки) — детерминированно в диспетчере; ИЛИ Эмма распознала
   просьбу в свободной форме — в system-блок добавляется инструкция
   «если клиент просит живого человека/менеджера — добавь маркер
   {{handoff}}», воркер парсит маркер (тот же парсер, что для файлов).
2. Что видит клиент (уточнение QA — тексты не дублируются):
   **кнопка** → уходит настроенный текст подтверждения (вкладка 5),
   Claude не вызывается; **маркер** → уходит собственный ответ Эммы с
   вырезанным маркером (она сама формулирует «сейчас позову менеджера»
   по инструкции из system-блока), текст подтверждения НЕ шлётся вторым
   сообщением.
3. Лид переводится в `dialog_mode=human` (существующий механизм M13 —
   Эмма замолкает, работают напоминания 10+10). **Автоподхват Эммы через
   10+10 минут сохраняется и здесь** (решение владельца, QA 2026-07-11):
   если менеджер не ответил, Эмма возвращается — извиняется, поясняет,
   что менеджер подключится позже, и продолжает помогать. Логика M13
   не меняется.
4. Менеджерам уходит WS-событие `dialog_mode` с новой причиной
   `client_handoff` (расширение перечня reason в `events`) — карточка
   в Kanban подсвечивается «требует ответа»; плюс уведомление в
   `alert_chat_id`, если настроен.
5. Менеджер отвечает через существующий чат M12. Кнопка «Взять в работу»
   уже есть (M13).
6. Событие `handoff` пишется в `emma_events` (счётчик на вкладке 6).

Стадии Kanban, state machine и TTL **не меняются**. Менеджер, как и сейчас,
не видит промпт, ключи и содержимое панели (доступ по роли).

## 9. Критерии приёмки (сквозные)

1. Менеджер (`role=manager`) не видит пункт меню и получает 403 на любой
   `/api/emma/*`; admin без PIN-сессии — 401 с кодом `PIN_REQUIRED`.
2. 5 неверных PIN → 429 на 15 минут; верный PIN после разблокировки работает.
3. Изменённый промпт влияет на ответ Эммы без рестарта процесса (≤30 с);
   откат версии возвращает и промпт, и темы, и стиль.
4. Загруженный PDF через ≤2 мин имеет статус `indexed`, и Эмма отвечает
   на вопрос, ответ на который есть только в этом PDF (живой тест на dev).
5. Файл с описанием «отправь при вопросе о ценах» реально уходит клиенту
   при вопросе о ценах; в чате M12 виден след `[файл: …]`.
6. Кнопка «Связаться с менеджером» и фраза «позовите человека» переводят
   диалог в `human`, Эмма молчит, менеджеру приходит WS-событие.
7. Все существующие тесты зелёные (baseline 2026-07-11: go test ./... ok,
   web 56 unit ok); e2e Эммы, ждущие автоответа, держат режим `bot`.
8. schema-lint проходит; `go test -p 1` в CI.

## 10. Закрытые вопросы отшлифовки (решения владельца, 2026-07-11)

1. Handoff-триггеры — **только распознавание Эммой** (маркер `{{handoff}}`)
   плюс кнопка; жёсткий список фраз не вводим (ложные срабатывания).
   Кнопка остаётся гарантированным путём без LLM.
2. Reply-клавиатура с кнопкой менеджера — **сразу с приветствия**.
3. Учёт токенов и примерной стоимости Claude — **добавлен** на вкладку
   Статистика (поля `tokens_in`/`tokens_out` в `emma_events`, EP-06).
4. Алерты шлёт **сама Эмма** в группу владельца; падение самого процесса
   CRM покрывает Prometheus/Alertmanager (M11), панель не дублирует.
5. Файлы для отправки — **только PDF/JPG/PNG**, DOCX исключён
   (редактируемые документы клиентам не отдаём).

Дополнительно после QA-прогона ТЗ против кода (2026-07-11):

6. Бюджет system-блока — **поднять 2000 → 5000 токенов** (при 2000
   секции панели вытесняли RAG-чанки полностью; потолок входных токенов
   становится 11000, отклонение от SRS §7.2 фиксируется в CLAUDE.md).
7. Автоподхват Эммы (M13, 10+10 мин) **сохраняется** и для handoff по
   просьбе клиента — лучше Эмма через 20 минут, чем тишина ночью;
   логика M13 не меняется.
